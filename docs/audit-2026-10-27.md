## P0 — 阻塞级

### A1 `ros2 run` / `ros2 launch` 不可用（可执行文件装错目录）

> **状态**：已修复（`3538e2a`）。`RUNTIME DESTINATION lib/${PROJECT_NAME}`。

**证据**

- `src/foray_localization_ros/CMakeLists.txt:85` 写的是 `RUNTIME DESTINATION bin`，因此
  `install/foray_localization_ros/bin/localization_node`、`bin/map_server_node` 装到了包前缀的 `bin/`，
  而 ROS 2 的 `ros2 run` / `ros2 launch` 只认 `lib/<package_name>/`。
- `ros2 pkg executables foray_localization_ros` 输出为空。
- 实测 launch 直接抛异常（原文）：

  ```
  [ERROR] [launch]: Caught exception in launch (see debug for traceback):
  package 'foray_localization_ros' found at '/ws/install/foray_localization_ros',
  but libexec directory '/ws/install/foray_localization_ros/lib/foray_localization_ros' does not exist
  ```

- `src/foray_localization_reslocalization`（重定位包）同样只有 `bin/`，没有 `lib/<pkg>/`，`ros2 run` 同样不可用。
  对比 `src/foray_localization_tools/CMakeLists.txt:19` 用的 `DESTINATION lib/${PROJECT_NAME}` 是正确的。

**影响**：`src/foray_localization_bringup/launch/localization.launch.py:52,60` 声明的两个节点一个都起不来，
README「兵种 launch 可分别启动」这条验收无法成立。

**建议**：`core / map / relocalization / ros` 四个包的 `install(TARGETS ...)` 全部改成

```cmake
ARCHIVE DESTINATION lib
LIBRARY DESTINATION lib
RUNTIME DESTINATION lib/${PROJECT_NAME}
```

并在 CI 里加一条「`ros2 pkg executables foray_localization_ros` 非空 + `ros2 launch ... --print` 能解析」的冒烟测试。

### A2 里程计时间戳早于点云时间戳 → 永久 `LOST`（状态机死锁）

> **状态**：已修复（`25b622c`）。健康状态机对小幅时间戳反序容错，不再返回 `+inf` 年龄。

**根因链**

1. `src/foray_localization_ros/src/localization_node.cpp:281,313` 用**点云时间戳**作为健康评估的 `now_ns`：
   `health_status_ = health_.update(sample, stamp_ns, odom_ns);`
2. `odom_ns` 是最近一次里程计回调的**最新**时间戳（`last_odom_ns_`）。里程计 50–100 Hz、点云 10 Hz，
   所以 `last_odom_ns_` 天然比当前点云时间戳新几十毫秒。
3. `src/foray_localization_core/src/health.cpp:18-23`

   ```cpp
   double age_seconds(Timestamp now_ns, Timestamp then_ns) {
       if (then_ns <= 0 || now_ns < then_ns) {
           return std::numeric_limits<double>::infinity();
       }
   ```

   只要 `now < then` 就返回 `+inf`。
4. `src/foray_localization_core/src/health.cpp:113-120` 用这个 `odom_age` 判断流：

   ```cpp
   const double odom_age = age_seconds(now_ns, last_odom_ns);
   if (!std::isfinite(odom_age) || odom_age > config_.odom_timeout_sec) {
       ... transition(HealthState::kLost, "odometry timeout", now_ns);
   ```

   于是**时间戳顺序反转 1 个 tick 就被判成"里程计断流"**，并且 `LOST` 是粘滞状态（只有人工
   `Relocalize` 能 reset），`map_to_odom_` 从此不再更新。

**实测证据**（Release 构建、仿真回放、5 Hz 配准、50 Hz 里程计，探针打印点云与里程计时间戳差）：

```
[audit] align dt_cloud_minus_odom_ms=-80.0 src=348 inlier=1.000 res=0.044 ...
[audit] state=lost valid=1 conf=0.00 reason=odometry timeout
```

- `dt_cloud_minus_odom_ms ≈ -80 ms`（点云比里程计旧 80 ms），**每一帧都如此**；
- 配准其实成功（`inlier=1.000`），但状态机在配准质量判断之前就返回 `LOST`，位姿永远不被采纳；
- 14 s 内 701 个状态采样，`state` 全程 `LOST`、`confidence` 全程 0。

**影响**：README「启动后 3 s 内 `OK`」不可能达成；这是"能编译、能过单测、一跑就死"的典型形态。

**建议**（任选其一，推荐 1+2）：

1. 健康评估统一用节点当前时间 `now()`，而不是点云时间戳；
2. `age_seconds` 对小的时间戳反序做容差（例如 `|Δ| < 0.2 s` 视为 0），只有真正的大幅反序才视为异常；
3. 给 `HealthMonitor` 补一条单测：`now < last_odom` 且差值在 1 个周期内时**不得**进入 `LOST`
   （现有 `test_health.cpp` 只测了 `last_odom_ns = 0` 和 `now - odom > timeout` 两个极端）。

### A3 仿真点云不是"激光"，M2 仿真验收无效

> **状态**：已修复（`99da264`）。射线投射改在传感器系进行，合成点云随位姿变化。

**根因链**

1. `src/foray_localization_tools/scripts/sim_common.py:199-215` 的 `RangeImage` 用
   `dist = math.sqrt(x*x + y*y + z*z)`（`:203`）建索引，即**以地图原点为观测原点**的距离图；
   `range_at(azimuth, elevation)`（`:217`）只有方向参数、没有观测原点参数。
2. `sim_common.py:240-268` 的 `raycast` 里旋转做了两次转置并且互相抵消：
   `rot[i][j] = pose[j][i]`（即 `rot = Rᵀ`），随后
   `wx = trans + distance * rot·d`（`:255-257`，等于 `t + Rᵀd`），再
   `p = w - t`（`:261`），最后发布点 `= rotᵀ·p = R·p = d·distance`。
   **结果：发布出来的点与 `pose` 完全无关**，就是"地图原点出发的射线落点"，也就是地图表面点本身。

**实测证据**（Release 构建，机器人真值已移动到 `x≈1.0 m`，里程计给出的初始猜测 `guess=(1.02,0,0.14)`）：

```
[audit] align src=351 inlier=1.000 res=0.045 fit=0.946 guess=(1.02,0.00,yaw=0.14) est=(0.00,0.01,yaw=0.00)
```

- `guess` 已经是真值附近，但 ICP 把解拉回**地图原点**（`est≈(0,0)`），残差依然 0.045、内点率依然 1.000；
- 只有当猜测离原点太远时 ICP 才会滑到别的局部极小（`est=(2.89,0.15)`、`inlier=0.53`）。
  这正是"点云与位姿无关，永远在地图原点附近拟合"的特征，真实传感器点云不可能出现这种恒定残差。

**影响**：`sim_replay.py --ros` 与 `--dump-dir` 两条链路都在喂"作弊点云"，因此
`eval_trajectory.py` 的 ATE/RPE、抖动、断流降级这些 M2 验收证据全部不成立；
这也是 A2 长期没被发现的原因之一（ICP 看起来"收敛得又好又稳"）。

**建议**

1. `RangeImage` 改为"先验地图 + 任意原点查询"（`range_at(origin, azimuth, elevation)` 或在
   `raycast` 内把方向先转到世界系再从 `pose` 打射线）；
2. `raycast` 里删掉多余的 `rot` 转置：世界点 `w = t + R·d`，传感器点 `p = Rᵀ·(w - t)`，两处转置不要互相抵消；
3. 加一条 Python 不变量测试（`sim_common` 级别即可）：同一帧点云在 `pose=(0,0,0)` 与
   `pose=(2,0,1.0)` 下**必须不同**，且把点云用真值变换回地图系后应与地图点到地图的最近距离 < 3σ。

## P1 — 高

### B1 激光断流 / 从未到达时，状态机不降级

> **状态**：已修复（`42c13c9`）。`HealthMonitor` 增加 `lidar_timeout_sec`（默认 0.2 s），
> `publish_state()` 用「最近一帧点云接收时刻」判定激光活性并喂 `valid=false` 样本。

`src/foray_localization_ros/src/localization_node.cpp` 里 `health_.update()` 只出现在两处：
配准回调（`:313`）与"里程计断流"分支（`:338,347`）。而配准回调在 `!has_cloud_` 时直接 `return`
（`:279-283`）。所以**没有点云 ⇒ 健康状态永不更新**，状态冻结。

**实测**：只发 50 Hz 里程计、10 s 内一个点云都不发 →
500 个 `/localization/state` 采样全部 `INITIALIZING`，且 `pose` 一直在发布（跟着里程计走）。

**影响**：README 要求「点云断流 ≤200 ms 进 `DEGRADED`、≤1 s 进 `LOST`，且不允许静默外推」，
实现在该场景下永远不满足；`HealthMonitor` 头文件里"任何失效都必须显式进入 DEGRADED/LOST"的承诺不成立。

**建议**：在 `state_rate_hz` 的定时器里用"当前时间 - 最近一帧点云时间"判断激光活性（与里程计断流同构），
超过阈值就喂一个 `valid=false` 的样本；`HealthMonitor` 增加 `lidar_timeout_sec`。

### B2 `LOST` 状态下 `/localization/state` 仍发布正常外观的位姿

> **状态**：已修复（`decision.md` D14）。采用建议中的第二种方案：`LocalizationState` 新增
> `bool pose_valid`（`pose` 之后、`confidence` 之前），`to_msg_state()` 由健康状态纯映射；
> `LOST`/`INITIALIZING` 期间照旧按 `state_rate_hz` 发状态（`confidence = 0`、TF 停发），
> 但 `pose_valid = false`，README「健康契约」写明下游必须检查后才能消费 `pose`。

`localization_node.cpp:356-362`：无论健康状态如何都会
`state_pub_->publish(to_msg_state(status, pose, ...))`，其中
`pose = map_to_odom_ * odom_to_base_`；`LOST` 时 `map_to_odom_` 停在最后一次成功值（初次启动为 `Identity`），
于是**发出的位姿恰好等于里程计位姿，看起来完全正常**，只有 `confidence=0` 能区分。
`map→odom` 的 TF 反而在 `LOST` 下被正确地停发了（`publish_tf()` 有 `kLost` 判断），两条链路行为不一致。

**影响**：下游（导航/决策）若只看 `pose`、不看 `state`，就是典型的静默外推。

**建议**：`LOST` 下要么不发布 `/localization/state`（只发 `DiagnosticStatus`），
要么在消息里加显式 `pose_valid` 字段并在文档中约定"必须检查"；
README 的接口表也应写明这条约定。

## 附：性能实测（供选型参考，非缺陷）

同一份 `IcpAligner`、同一份数据（368 源点 / 4668 地图点 / 20 次迭代）：

| 构建 | 单帧配准耗时 |
|---|---|
| `-O0`（`colcon build` 不带 build type） | 528 ms（独立基准）/ 1.2–1.8 s（节点内实测） |
| `-O3 -DNDEBUG`（`CMAKE_BUILD_TYPE=Release`） | **6.3 ms**（独立基准）/ 16.7–20.2 ms（节点内实测） |

结论：README `:22` 与 CI 都用 `-DCMAKE_BUILD_TYPE=Release`，因此 5 Hz（200 ms 预算）是满足的；
但若有人按直觉 `colcon build`（无 build type），Eigen 未优化会把单帧拖到 0.5–1.8 s，
状态发布被单线程执行器饿到 ~2.5 Hz。建议在 `CMakeLists.txt` 里显式
`if(NOT CMAKE_BUILD_TYPE) set(CMAKE_BUILD_TYPE Release) endif()`，并加一条启动自检日志
（打印 `NDEBUG`/优化标志），避免"未优化构建"被当成算法性能问题排查。

## 附：环境备注

宿主机工作树里残留 `local/`（conda 工具链缓存）、`log/`、`.pytest_cache/` 等目录，被 `.gitignore` 忽略，
但**在仓根直接 `colcon build` 会报 `Duplicate package names not supported`**（colcon 把
`local/toolchain/pkgs/.../site-packages` 也当包扫描了）。本次审计用 `--base-paths src` 规避。
建议文档里给一条"仓根构建前清理/加 `COLCON_IGNORE`"的说明，或把这些临时目录放到仓外。
